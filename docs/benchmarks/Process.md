# 측정을 어떻게 만들었나

12개 에이전트 루프를 비교하기 위해 평가 과제와 채점 방식, 실행 하네스를 구성했다.
여기서는 어떤 과제를 선택했고, 측정하면서 하네스를 어떻게 수정했는지만 정리한다. 실제 측정 결과는 측정별 문서에 따로 기록한다.

## 1. 평가 과제 선정

처음에는 BFCL의 파일 관리 과제로 12개 루프를 비교했다.

BFCL은 함수 호출 능력을 비교하기에는 적합했지만, 파일시스템 자체는 시뮬레이션되어 있다. 그래서 실제 환경에서 생기는 경로 해석 오류, 일부 작업만 실행하는 문제, 잘못된 파일 조작 같은 것은 확인하기 어려웠다.

이후에는 **실제 워크스페이스에서 파일을 직접 조작하고, 작업이 끝난 뒤의 파일 상태를 확인할 수 있는 과제**를 추가했다.

과제는 다음 조건으로 골랐다.

- 공개 데이터이고 사용 가능한 라이선스일 것
- 정답이나 검증 코드가 제공될 것
- 파일 이동, 복사, 이름 변경, 압축 등 파일 관리 작업이 중심일 것

원본 요청, 정답, 채점 코드는 수정하지 않고 이번 측정에 맞는 과제만 선별했다.


| 후보                      | 사용 여부     | 내용                                         |
| ----------------------- | --------- | ------------------------------------------ |
| BFCL v4 multi_turn      | 기준선       | 시뮬레이션 파일시스템. 함수 호출 자체를 비교하는 용도로 사용         |
| MCPMark Filesystem      | 40건 중 21건 | 실제 워크스페이스와 과제별 검증 스크립트 제공                  |
| InterCode-Bash          | 26건 중 20건 | 정답 셸 명령을 실행한 결과와 모델 결과를 비교할 수 있음           |
| Terminal-Bench, NL2Bash | 제외        | 데이터 처리나 복잡한 셸 파이프라인 비중이 높아 이번 평가 범위와 맞지 않음 |


MCPMark에서는 문서 해석이나 계산이 중심인 19건을 제외했고, InterCode에서는 요청과 제공된 정답이 맞지 않는 6건을 제외했다.

## 2. 공통 과제 형식

MCPMark와 InterCode는 과제를 제공하는 방식이 다르다.

MCPMark는 시작 워크스페이스와 `verify.py`를 제공하고, InterCode는 초기 파일을 만드는 셸 스크립트와 정답 셸 명령을 제공한다.

벤치마다 별도의 실행 코드를 만들면 루프 비교 조건도 달라질 수 있기 때문에, 하네스에서는 두 벤치를 같은 형식으로 다루도록 했다.

각 과제에는 다음 정보만 넣는다.

- 시작 워크스페이스
- 사용자 요청
- 정답 또는 기대 결과
- 채점 방식

`run_tasks.py`는 이 공통 형식만 처리한다. MCPMark와 InterCode의 차이는 과제를 불러오는 단계에서 처리한다.

### MCPMark

MCPMark는 제공된 워크스페이스와 검증 스크립트를 그대로 사용한다.

다만 일부 과제는 파일의 수정 시각을 조건으로 사용한다. 저장소에서 파일을 다시 받으면 원래 수정 시각이 사라지기 때문에, 원본 파일의 수정 시각을 별도로 저장하고 워크스페이스를 만들 때 복원하도록 했다.

### InterCode

InterCode는 원래 Docker 환경을 기준으로 만들어져 있다.

측정에서는 Docker 없이 동일한 파일 상태를 만들 수 있도록 원본 설정 스크립트를 워크스페이스 기준으로 실행한다.

채점할 때는 동일한 초기 상태에서 정답 셸 명령도 실행한다.

```text
초기 워크스페이스
├─ 모델 실행 → 모델 결과
└─ 정답 실행 → 정답 결과

모델 결과 ↔ 정답 결과 비교

```

일반 파일은 내용과 경로를 비교하고, 압축 파일은 압축 파일 자체의 바이트가 아니라 내부 파일을 비교한다. 심링크는 링크가 가리키는 경로를 비교한다.

현재 하네스에서는 세 가지 채점 방식을 사용한다.

- MCPMark의 검증 스크립트
- InterCode의 정답 실행 결과와 상태 비교
- 정답이 하나로 정해지기 어려운 과제를 위한 규칙 기반 채점

규칙 기반 채점은 이후 한국어 실사용 과제에서 사용한다. 파일이 실제로 변경됐는지, 이동이나 복사 같은 필요한 동작이 수행됐는지, 필요한 문자열이 인자나 최종 응답에 포함됐는지 등을 확인한다.

## 3. 하네스 수정

실제 측정을 돌리면서 하네스 쪽에서도 몇 가지 문제가 발견됐다.

특정 모델이나 특정 문제를 통과시키기 위한 예외를 추가하지는 않았다. 수정이 필요한 경우에는 Codex, opencode, Deep Agents 등 공개된 CLI 에이전트 구현에서 일반적으로 사용하는 방식을 참고했다.

주요 변경 사항은 다음과 같다.

- 도구 실행 결과를 JSON 대신 평문으로 전달
- 텍스트 기반 루프도 동일한 도구 결과 형식 사용
- 모델 응답이 비거나 중간에 잘린 경우 재시도하지 않고 종료
- 빈 응답, 잘림 등 종료 원인을 결과에 별도로 기록
- 스텝 예산이 라운드나 도구 호출 수를 기준으로 하는 루프에도 동일하게 적용되도록 수정
- 솔버, 반성, 조이너 같은 보조 역할에서는 메인 루프의 계획 지시 제거
- 실제 도구 호출 없이 본문에 도구 호출 형식만 출력하는 경우를 별도 실패로 감지
- Bash의 `HOME`을 워크스페이스 밖으로 지정해 캐시 파일이 채점에 포함되지 않도록 처리
- `--keep-workspaces` 옵션으로 실행이 끝난 워크스페이스를 보관

마지막 옵션은 자동 채점 결과와 실제 파일 상태가 맞는지 확인할 때 사용했다.

## 4. 샌드박스와 가드레일

초기 측정에서는 모델이 다음과 같은 명령을 생성한 경우가 있었다.

```bash
find / -type f -delete

```

당시에는 문자열 기준으로 위험 명령을 막고 있었는데 `/` 단독 경로를 제대로 처리하지 못했다.

처음에는 절대 경로를 모두 차단하는 방식으로 수정했지만, 정상적인 명령까지 막을 수 있다는 문제가 있었다.

현재 macOS 측정 환경에서는 셸 자체를 `sandbox-exec` 안에서 실행한다.

```text
모델
 ↓
Bash
 ↓
sandbox-exec
 ↓
Workspace

```

워크스페이스 밖에 대한 쓰기는 OS에서 차단하고, 기존 문자열 검사는 샌드박스를 사용할 수 없는 환경을 위한 보조 수단으로만 남겨두었다.

측정에서는 가드레일 때문에 특정 루프만 명령이 거부되는 상황도 피해야 했다. 따라서 기존 문자열 가드에서 거부된 케이스는 OS 샌드박스 조건에서 다시 측정했다.

## 5. 측정 방법

실제 측정은 다음 순서로 진행한다.

1. 모델 서버를 동일한 옵션으로 실행한다.
2. Thinking은 활성화하고 예산은 `2048`로 고정한다.
3. 각 루프에 같은 과제, 같은 도구, 같은 스텝 예산을 사용한다.
4. `--keep-workspaces`로 실행 후 워크스페이스를 보관한다.
5. 각 벤치의 채점 결과를 그대로 기록한다.
6. 실패 케이스는 검증 결과와 실제 실행 명령을 확인해 원인을 분류한다.
7. 도구 호출 오류와 잘못된 도구 이름, 인자 오류도 함께 집계한다.

최종 성공률만 보는 것이 아니라 **왜 실패했는지**를 같이 확인한다.

예를 들어 같은 실패라도 다음과 같이 구분한다.

```text
대상을 잘못 선택함
명령을 일부만 실행함
도구 호출 없이 답변만 함
없는 도구를 호출함
인자를 잘못 생성함
응답이 중간에 종료됨

```

측정이 끝나면 조건과 사용한 코드 커밋을 별도 문서에 기록한다. 같은 과제를 다시 측정하더라도 기존 결과를 수정하지 않고 새로운 측정으로 남긴다.
