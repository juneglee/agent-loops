## 도구 호출

4,847회 실행. 오류율은 Bash 17.8%, Glob 19.1%, Write 6.7%, Read 0.5%. 없는 도구 이름은 0회, `Read` 에 `path=` 를 쓴 인자 오류 59회, `Edit` 는 한 번도 호출되지 않았다.

## 읽는 법

1. **오류를 보고 고치는 루프가 앞선다.** 첫 툴 오류 뒤 다른 인자로 성공한 비율은 피드백 루프(`dfsdt`·`plan_and_execute`·`reflexion`·`react`)가 90~100%, 계획을 미리 고정하는 루프(`plan_and_solve` 20%, `single_call` 0%)는 첫 오류에서 무너진다.
2. **그 위에 얹은 기구가 새 실패를 만든다.** `plan_and_act` 의 형식 오류, `dfsdt` 의 중복 분기, `adapt` 의 분해 실패, `reflexion` 의 시도 3회 반복. `react` 는 "관측 → 다음 행동" 외에 기구가 없어 고유 실패 모드가 없다.
3. **과제가 짧아 계획 비용이 회수되지 않는다.** 통과 케이스의 툴 실행은 3~10회다. `plan_and_execute` 의 계획 응답 266개 중 263개가 한 단계짜리라, 실제로는 `react` 와 같은 일을 라운드당 호출 2배로 한다.
4. **함수 호출 채널이 유리하다.** `#E1 = tool[arg]` 같은 텍스트 계획 문법을 4B 모델이 직접 써야 하는 루프에서 parse 실패가 난다.

## 유보

41과제 1회 실행이라 1~2건 차이는 잡음이다. 확실한 것은 "피드백 있는 루프 > 없는 루프"라는 묶음 차이이고, `react`·`codeact`·`plan_and_execute`·`reflexion`·`dfsdt` 사이 순위는 반복 측정 없이 단정하지 않는다.
